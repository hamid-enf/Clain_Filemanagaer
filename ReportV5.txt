## 5. New findings (IMG-NEW-XX)

### IMG-NEW-01 (confirmed, medium severity) - Image_DecodeJPEG has no software fallback when a hardware JPEG codec is registered

**File/function/line:** src/fm_image.c (Image_DecodeJPEG) and src/fm_jpeg.c (FM_JPEG_LoadFile and jpeg_sw_decode_src)  
**Precondition:** A hardware JPEG codec is registered via Image_RegisterCodec("JPEG", ...) and the image is full-size (dw == inf.width && dh == inf.height).  
**Reproduction:** Call Image_DecodeJPEG() on a complete JPEG while a hardware JPEG codec is registered and hw->decode() fails (e.g., peripheral unresponsive or unsupported marker).  
**Expected:** If the hardware codec fails, the software decoder (picojpeg) should run as fallback, as FM_JPEG_LoadFile (file path) does.  
**Actual:** Image_DecodeJPEG returns `hw->decode(...)` directly and returns the hardware error to the caller **without any software fallback**. In contrast, FM_JPEG_LoadFile (file path) falls back to jpeg_sw_decode_src on hardware failure.  
**Cause:** Design inconsistency between the two entry points (Image_DecodeJPEG is memory-based; FM_JPEG_LoadFile is file-based).  
**Suggested fix:** In Image_DecodeJPEG, when a hardware codec is registered but decode fails or conditions are unsuitable, fall back to jpeg_sw_decode (same pattern as FM_JPEG_LoadFile).  
**Regression test:** Build a test that registers a failing/simulating hardware codec and calls Image_DecodeJPEG; expect PASS via the software decoder.

### IMG-NEW-02 (design limitation / hypothesis, not a memory-safety defect) - BMP stream downscale is rejected when the full source row exceeds FM_IMAGE_LINE_MAX

**File/function/line:** src/fm_image.c (image_load_stream); FM_IMAGE_LINE_MAX in include/fm_config.h (16 KiB)  
**Precondition:** A BMP whose width makes width*bpp > FM_IMAGE_LINE_MAX (e.g., 6000 px RGB -> 18,000 bytes > 16,384) and you want to downscale (Image_LoadEx with max_w/max_h).  
**Reproduction:** Encode a 6000x10 BMP, then call Image_LoadEx(..., 100, 10) (verified).  
**Expected:** The downscaled 100x10 image fits in the 3,000-byte buffer.  
**Actual:** FM_ERR_TOO_LARGE because the full source row (18,000) does not fit in the static scratch g_image_line (16,384), even though the downscaled output is small.  
**Cause:** The BMP stream downscale path holds one full source row in static scratch; this scratch limit is configurable.  
**Suggested fix:** For downscale, read the source row in chunks, or raise FM_IMAGE_LINE_MAX (it is a tunable constant; small MCUs have limited RAM).  
**Regression test:** A BMP wider than 5,461 px (RGB) plus downscale -> expect FM_ERR_TOO_LARGE (documented) or successful load with larger scratch.

## ۵) یافته‌های جدید تأییدشده
### VID-NEW-01 — H.264 Annex-B trailing start code OOB read
- شدت: S2/High
- مسیر/تابع/خط: `src/fm_h264.c:h264_blob_is_keyframe:386`؛ الگوی مشابه در `h264_blob_scan_nals:324`
- پیش‌شرط: `FM_USE_H264=1`؛ فراخوانی codec plugin با payload که دقیقاً به `00 00 00 01` ختم می‌شود و بایت NAL header بعدی وجود ندارد.
- ورودی: ۴ بایت heap_exact `00 00 00 01`؛ همچنین از مسیر container/frame مخرب قابل تحویل است.
- بازتولید: `_audit/harness/h264_probe.c trailing 4` با ASan.
- واقعی: `AddressSanitizer: heap-buffer-overflow READ of size 1` در `fm_h264.c:386`، exit 1.
- انتظار: خواندن خارج از بافر ممنوع؛ start code بدون NAL header باید رد/نادیده گرفته شود.
- علت: شرط `while (i + 4 <= n)` برای start code چهاربایتی کافی نیست؛ سپس `s[i + sc]` وقتی `i+sc==n` خوانده می‌شود.
- اصلاح پیشنهادی: قبل از خواندن type، `i + sc < n` را الزام کند؛ برای start code سه‌بایتی نیز `i + 3 < n`. حلقه/پیمایش بعدی باید مرز `n` را رعایت کند.
- رگرسیون: exact trailing `00 00 00 01` و `00 00 01` زیر ASan/UBSan؛ چند NAL سالم با/بدون trailing start code.
### VID-NEW-02 — SimpleVideo_Begin re-entry leak / stale I2S
- شدت: S2/High
- مسیر/تابع/خط: `top_api/simple_video.h:SimpleVideo_Begin:2809`؛ twin در `examples/simple_video.h`
- پیش‌شرط: `SimpleVideo_Begin()` بیش از یک بار بدون `SimpleVideo_Stop()`؛ چه idle و چه در حال پخش.
- ورودی: playlist ساده `/videos/clip.avi`؛ حالت running با I2S stub.
- بازتولید: `_audit/harness/sv_probe.c begin_leak 4` و `begin_running`.
- واقعی:
  - idle: `live_blocks` 1→4؛ LSan: `Direct leak of 7872 byte(s) in 3 object(s)` از `scan_cb → Player_ScanFolder → SimpleVideo_Begin`.
  - running: `rebegin`ها `live` را زیاد کردند، `i2s=1` باقی ماند، و ظرفیت `Video_Open` اضافی از ۴ در control به ۳ کاهش یافت.
- انتظار: Begin باید یا حالت قبلی را کامل teardown کند (playlist/file/codec/I2S/present) یا در حالت running خطای BUSY بدهد؛ نشت handle/heap و DMA روشن مجاز نیست.

## 0. Read this first — three corrections to earlier findings
The previous audit round reported two candidate defects. Both were **re-examined in this round and found to be defects of the test harness, not of the product.** They are recorded here so that they are not carried forward as product bugs.
| Prior candidate | Status now | Why |
|---|---|---|
| "ID3v2.2 behind an MP3 truncates the track to 6912 samples (FFmpeg: 178560)" | **Retracted — test defect** | The fixture was built with an 8-byte v2.2 header (3-byte plain size). The ID3v2.2 specification states the tag header is **10 bytes with a 4-byte synchsafe size**, identical to v2.3/v2.4. With a spec-conformant v2.2 tag the library returns 176400 samples, exactly matching FFmpeg. |
| "A valid ID3v2.2 tag in front of a WAV/FLAC is rejected with `-17`" | **Retracted — test defect** | Same wrong header layout. With a conformant tag, WAV (22050 samples), FLAC (22050) and MP3 all open and match FFmpeg. |
**Source for the corrected layout:** the ID3v2.2 specification defines *"ID3 size: 4 * %0xxxxxxx"*, i.e. a 4-byte synchsafe integer in a 10-byte header — the three-byte sizes belong to the *frames*, not to the tag header. See §10 for the citation.
Consequence: the earlier "ID3v2.2" line of investigation is closed. The remaining ID3 findings below are different and are backed by mutation witnesses.

Two callers in the same file, `SimpleAudio` (`examples/simple_audio.h`, `SA_CMD_SEEK` at ~line 906 vs `SA_CMD_RESUME` at ~line 831), handle the two results with different control flow. Evidence: `Audio_Seek(1e6)` on 6 codecs → MP3 `-15`, all others `0` |
| `AUD-NEW-05` | info | confirmed (contract limitation, documented) | WAV PCM widths | `src/fm_audio.c:audio_parse_wav` | — | 24-bit, 32-bit, 32-bit float and >2-channel WAV are refused with `FM_ERR_UNSUPPORTED` while FFmpeg decodes them. The README table states exactly this, so this is **not** a defect — recorded so the refusal is not mistaken for corruption. Note the asymmetry: the **video** layer decodes 24/32-bit and float PCM, the **audio** layer does not. |
| `AUD-NEW-06` | info | confirmed (by design) | `Audio_Read` frame alignment | `src/fm_audio.c:Audio_Read` | — | A `count` that is not a whole number of frames returns `FM_ERR_INVALID_ARGUMENT` and zero samples. The behaviour is correct and deliberate (documented in the `.c` file) but the **public header** only says "Read up to count samples". A stereo caller passing `count=3` silently gets an error instead of one frame. Proposal: document it in `include/fm_audio.h`. |
### 3.1 What is *not* a finding
Two crashes were produced by the audit's own harnesses and are **not** product defects; they are listed so they are not mistaken for bugs:
* a harness passed `count = SIZE_MAX/2` with an 8 192-sample buffer, and another passed `SIZE_MAX/4`. `Audio_Read` honours `count` by contract, so the harness overran its own buffer (MP3 path segfault, WAV path silent clamp). Crashes caused by violating the documented buffer-size contract.
* a harness passed `%s` for an enum field and segfaulted in `printf`.
Neither indicates a library defect.

### 5.1 The survivors, analysed honestly
* **`M01`, `M03`, `M11` — real coverage gaps.** Each mutation changes observable output, each is caught by something that exists in the repository, and each is invisible to `make test`. These are the three items behind `AUD-NEW-01` and `AUD-NEW-02`.
* **`M04` — equivalent mutant, not a gap.** The mutation makes a tag whose declared size runs past EOF skip to the end of the file instead of returning `FM_ERR_INVALID_FORMAT`. Probed with four fixtures (tag ending exactly at EOF, tag overrunning into audio, zero-length tag, second tag of a chain overrunning): the mutated build produces **identical** results to the baseline in all four, because the MP3 opener independently rejects an audio start at or past EOF. The failure path is unreachable from that entry point, so no test can distinguish the mutant. Not a defect.
* **`M10` — defensive-only, not a gap.** The mutation decodes the whole ADPCM block instead of only the bytes actually read. Probed with a truncated final block (two cut points) and with a `data` chunk that claims 20 000 bytes more than the file holds: **byte-identical PCM** to the baseline in all three. The `got_bytes` clamp matters only when a read returns short *inside* the final block, which the host backends never do. Keep the guard (it is correct on a flaky SD card) but do not expect a host test to reach it.
* **`M12`** segfaults the suite rather than failing an assertion. That is a crash of the *mutated* build, and it does mean the suite notices — but the diagnosis is poor. Worth a `-fsanitize` run in CI so such a mutation reports a line instead of a signal.

## 8. Audio/video boundary
Checked and correct in this round: `Video_ReadAudioFrame` returns 16-bit PCM for 24-bit, 32-bit, 32-bit float and big-endian PCM, for FLAC-in-MP4, IMA and MS ADPCM, MP3-in-AVI and Vorbis-in-MKV — all eight vectors report `decodable=1` and deliver audio. The audio layer's refusal of 24-bit WAV while the video layer accepts 24-bit AVI/MKV/MP4 PCM is a **deliberate asymmetry** that the README states; it is recorded as `AUD-NEW-05`, not a defect.

## 9. Limitations and NOT RUN
Everything in this section is **not evidence**, and no conclusion above depends on it.
1. **No hardware was used.** No board, no I2S, no real DMA, no SD card, no codec chip, no speaker, no oscilloscope or audio analyser. The `AudioDma` witness is a host model of a double buffer; it proves sample bookkeeping, **not** timing, jitter or underrun behaviour.
2. **No power-loss testing.** The WAV "recording never closed" path is exercised by constructing the file, not by cutting power.
3. **No long-duration replay.** No 10-hour play, no track-count stress, no memory-fragmentation run.
4. **No real SD-card fault model.** `FM_ERR_IO`/short reads are injected synthetically. `M10` shows the short-read guard is unreachable on the host backends.
5. **No concurrency stress beyond TSan.** TSan reports zero warnings, but no multi-task scheduling pattern resembling an audio ISR plus a decoder task on one core was simulated.
6. **Stack figures are quoted from the README**, not re-measured.
7. **No `.m4a`/AAC outside ADTS.** AAC decoding itself is a *plugin*: the framing layer was audited with a synthetic plugin, so **the behaviour of any real AAC decoder is outside this audit**.
8. **FFmpeg 9.0.2 is the reference decoder**, not an absolute truth. A disagreement with FFmpeg is a prompt to investigate one side or the other — as §0 demonstrates, twice, in the harness's favour.

## 12. Executive summary
The audio subsystem at `ddd1b3e0` is in **good shape on everything that was actually exercised**: 684/684 on the host suite, 685/685 on a 32-bit build, 8/8 feature configurations, clean ASan/UBSan/TSan, exact PCM agreement with FFmpeg for MP3, ADPCM and G.711, correct gapless behaviour under the project's own differential tool, correct ID3 handling for conformant v2.2/v2.3/v2.4/chained/footer tags, correct resync over damaged AAC, and correct sample bookkeeping through `Audio_Convert`, `AudioDma` and the container audio path.
**No new product defect was proven in this round.** Two previous "candidates" were retracted as harness errors (§0) — the ID3v2.2 story was simply wrong about the header layout. What remains is **three confirmed coverage gaps** (`AUD-NEW-01/02/03`), all in the *test suite* rather than the library, and **two documentation inconsistencies** (`AUD-NEW-04/06`).
The highest-value action is not a code change: **`tools/test_mp3_gapless.py` exists, is correct, catches two of the three surviving mutations immediately, and nothing ever runs it.** Wiring it into `make test` would close the largest correctness gap in the subsystem's verification for a few lines of Makefile.

## ۳) ماتریس ورودی × انکودر × کانتینر × بک‌اند × نوع خطا

### ۳-۱) ابعاد ماتریس
- **انکودر/کانتینر صوتی:** PCM→WAV (هدر ۴۴ بایتی)، IMA-ADPCM→WAV (هدر ۶۰ بایتی با `fmt ` tag 0x11 + `fact`)، FLAC بومی (هدر ۵۸ بایتی: `fLaC` + STREAMINFO(34) + VORBIS_COMMENT)، و `AUTO` (تشخیص از پسوند). MP3/VORBIS/OPUS نیازمند `Audio_RegisterEncoder` → در این build **NOT RUN** (انکودر ثبت‌نشده = `FM_ERR_UNSUPPORTED`).
- **انکودر/کانتینر ویدیویی:** MJPEG-in-AVI (نویسندهٔ `fm_video_enc.c`) با و بدون صدا؛ مسیر FMRV فقط بازبینی کد.
- **ورودی:** ۷ الگوی PCM شامل سکوت، دو تُن، موج مربعی تمام‌مقیاس (±32767 و −32768)، نویز سفید؛ نرخ‌های 8000/16000/22050/44100/48000 و نرخ فرد؛ mono/stereo؛ mixdown و up-mix از طریق `out_channels`; اندازه‌های تکه ۱ تا ۴۰۹۶ فریم؛ تعداد فریم فرد (۴۰۹۷).
- **بک‌اند:** `backends/fm_posix_fs.c` (POSIX؛ `file_flush` = `fsync`) با تزریق خطا در لایهٔ `FM_FS` (جابه‌جایی pointerهای `FM_FS` محلی + `FS_Mount("/", &fs)`). FatFS واقعی و littlefs روی host فقط به‌صورت build/سوئیت (`make fatfs`) — نه به‌عنوان محیط ضبط.
- **انواع خطا:** شکست نوشتن در n-امین فراخوانی، نوشتن کوتاه، شکست flush، شکست close، شکست seek (patch هدر)، شکست truncate، سقف بایت (`FM_ERR_TOO_LARGE`)، و رهاکردن فرآیند با `_exit(9)` (مدل قطع برق).

## ۶) فرض‌ها و موارد بررسی‌نشده (جدا از یافته‌های قطعی)

**فرض‌های صریح**
1. build هدف، **۳۲ بیتی** با `size_t`/`uintptr_t` ۳۲ بیتی است؛ من این را با `zig cc -target x86-linux-musl` (ilp32) سنجیدم نه با toolchain واقعی ARM. فرض بر این است که `zig` همان اندازهٔ انواع را می‌دهد.
2. **هیچ ISR واقعی، DMA واقعی، I2S واقعی یا SD واقعی** در این ممیزی وجود ندارد. `AudioDma_HalfCallback`/`FullCallback` با دست فراخوانی شدند؛ «قطع برق» = `_exit(9)` فرآیند روی POSIX؛ «کارت پر» = تزریق در `FM_FS`. هیچ‌کدام **نتیجهٔ سخت‌افزاری** نیستند.
3. فرض شد بافرهای DMA هم‌تراز و در دسترسِ DMA هستند و `FM_Cache_CleanForDma` روی برد درست عمل می‌کند (روی host no-op است).
4. فرض شد `FM_Alloc` هرگز `NULL` برنگرداند جز در مواردی که خودم تزریق کردم؛ کمبود حافظهٔ واقعیِ mid-recording به‌طور سیستماتیک sweep نشد.
5. پیکربندی پیش‌فرض کامپایل در نظر گرفته شد: `FM_AUDIO_ENC_OUT_BYTES=16384`، `FM_FLAC_ENC_BLOCK=4096`، `FM_AUDIO_ENC_SYNC_BYTES=262144`، `FM_VIDEO_ENC_OUT_BYTES=32768`، `FM_VIDEO_ENC_QUALITY=80`، `FM_VIDEO_ENC_MAX_BYTES=0x7F000000`، `FM_VIDEO_ENC_SYNC_BYTES=1048576`.
6. اوراکل‌های دست‌ساز من پیش از استفاده **کالیبره** شدند: اوراکل AVI روی `ref_mjpeg.avi` ساختهٔ ffmpeg (۴۶۷۰۲ بایت) → ۰ اشکال، و اوراکل صوت روی `wave`/ffmpeg → بیت‌به‌بیت. دو خطای شناخته‌شدهٔ اوراکل خودم که در نتایج لحاظ شده‌اند: (الف) بررسی «fact ≤ blocks» بیش از حد سخت‌گیرانه است (بلاک آخر pad می‌شود) و (ب) مقایسهٔ bit-exact برای mixdown/up-mix معنا ندارد.

### ۷-۳) محدودیت‌های مدل cut (صریح)
- «قطع برق» = `_exit(9)` فرآیند. روی POSIX، بافرهای stdio و cache صفحه **ممکن است** بعد از `_exit` هم روی دیسک بنشینند؛ بنابراین این مدل نسبت به قطع برق واقعی **خوش‌بینانه‌تر** است. هیچ ادعایی دربارهٔ دوام واقعی SD/FAT انجام نمی‌شود.
- تزریق خطا در سطح `FM_FS` است، پس «نوشتن کوتاه» و «شکست flush» رفتار درایور FAT/SD را مدل نمی‌کنند (مثلاً write-amplification یا torn page).
- `File_Flush` در بک‌اند POSIX = `fsync`؛ روی FatFS معادلش `f_sync` است و هزینه/زمان‌بندی‌اش کاملاً متفاوت — نتیجهٔ «چند checkpoint در ثانیه» به برد منتقل نمی‌شود.
- مدل stall (SAV3-04) فراخوانی بازگشتی `AudioDma_HalfCallback` است؛ خود آزمون مخزن هم می‌گوید این «measurement of any real SD-card latency» نیست.

### محدودیت‌های host در برابر دستگاه واقعی (صریح)
1. **زمان‌بندی وجود ندارد.** روی host هیچ deadline واقعی نیست؛ بنابراین SAV3-04 و هر پرسش «آیا نوشتن کارت به نصفهٔ بعدی DMA می‌رسد؟» **اصلاً قابل پاسخ نیست**. آنچه اندازه‌گیری شد فقط *ساختار* است (۵ نوشتن/۸۱۹۲۰ بایت داخل `refilling[]`)، نه latency.
2. **`_exit(9)` ≠ قطع برق.** cache صفحه و journal فایل‌سیستم ممکن است داده را نگه دارند؛ مدل من خوش‌بینانه‌تر از واقعیت است. هیچ ادعایی دربارهٔ دوام SD انجام نمی‌شود.
3. **`File_Flush` = `fsync`** روی POSIX؛ روی FatFS = `f_sync` با هزینهٔ کاملاً متفاوت ⇒ «دورهٔ checkpoint بهینه» از این نتایج **قابل استخراج نیست**.
4. **bypass شدن cache/DMA.** `FM_Cache_CleanForDma` روی host no-op است؛ کلاس خطاهای هم‌ترازی/کش که فقط روی Cortex-M7 دیده می‌شود اینجا دیده نمی‌شود.
5. **اندازهٔ انواع.** build ۳۲ بیتی با zig/musl انجام شد، نه با toolchain واقعی ARM؛ رفتار `size_t` ۳۲ بیتی تأیید شد ولی ABI/alignment خاص ARM نه.
6. **هیچ ادعای «صفر باگ» نمی‌شود.** نبودِ یافته در یک پیکربندی به معنای نبودِ نقص در پیکربندی‌های آزموده‌نشده نیست.
