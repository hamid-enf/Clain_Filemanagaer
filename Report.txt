D-01  PNG dynamic Huffman tables are not validated (corrupt-input acceptance)
================================================================================
Class      : Correctness / robustness on malformed input (NOT a buffer overflow)
Location   : src/fm_png.c:142-205  (Huff, huff_build, huff_decode)
             src/fm_png.c:346-453  (inf_dynamic builds cl/lit/dist tables)
             src/fm_png.c:300-344  (inf_fixed, for comparison - valid tables)
Description:
  huff_build() only rejects code lengths > 15, then fills count[16] and
  symbol[288]. It never checks the Kraft inequality, over-subscription, or
  incompleteness. huff_decode() therefore accepts malformed canonical trees:
    - over-subscribed trees map bit patterns to wrong / unreachable symbols;
    - incomplete trees (except the one legal single-symbol case) are accepted;
    - an all-zero distance table is accepted and makes every distance decode
      fail only after 15 bits instead of being rejected up front.
  A corrupt PNG is silently decoded with wrong pixels instead of returning
  FM_ERR_CORRUPTED.
Cause:
  Missing canonical-code validation in huff_build(); no bounds check on the
  computed symbol index in huff_decode().
Measured evidence (verbatim fm_png.c statics, ASAN+UBSAN harness):
    huff_build({1,1,1}, 3) = 0   (over-subscribed, should be -1)
    huff_build({2},     1) = 0   (incomplete, should be -1)
    200000 randomized length tables + huff_decode() under ASAN+UBSAN:
    "huff fuzz done, no crash".
  IMPORTANT CORRECTION: an earlier suspicion that invalid tables make
  h->symbol[index + (code-first)] read out of bounds is DISPROVED. Because both
  `code` and `first` are shifted left each iteration, code >= first is
  invariant, and index + (code-first) < total symbols <= 288. This candidate is
  a corrupt-input / correctness defect, NOT an ASAN heap/global overflow.
Pseudo-fix:
    typedef struct {
        uint16_t count[16];
        uint16_t symbol[288];
        uint16_t nsym;              /* add */
    } Huff;
    static int huff_build(Huff *h, const uint8_t *lengths, int n)
    {
        int left = 1, len, i, k = 0, nonzero = 0, only = -1;
        memset(h, 0, sizeof(*h));
        for (i = 0; i < n; i++) {
            if (lengths[i] > 15) return -1;
            h->count[lengths[i]]++;
            if (lengths[i]) { nonzero++; only = i; }
        }
        h->count[0] = 0;
        for (len = 1; len <= 15; len++) {
            left <<= 1;
            left -= h->count[len];
            if (left < 0) return -1;            /* over-subscribed */
        }
        /* Deflate permits exactly one incomplete code: one symbol, length 1
         * (typical dummy distance tree). Everything else is invalid. */
        if (left != 0 &&
            !(nonzero == 1 && lengths[only] == 1)) return -1;
        for (len = 1; len <= 15; len++)
            for (i = 0; i < n; i++)
                if (lengths[i] == len) h->symbol[k++] = (uint16_t)i;
        h->nsym = (uint16_t)k;
        return 0;
    }
    /* inside huff_decode(), before returning: */
    int off = code - first;
    if (off < 0 || off >= count) continue;      /* explicit, UBSAN-friendly */
    if (index + off >= (int)h->nsym) return -1;
    return (int)h->symbol[index + off];

D-02  PNG Deflate accepts distances > 32768 (stale sliding-window reads)
================================================================================
Class      : Correctness / corrupted output / stale data disclosure
Location   : src/fm_png.c:229-266  (inf_put, inf_copy)
             src/fm_png.c:216-224  (k_dist_base: max 24577 + 13 bits = 32768)
             include/fm_config.h:149-150 (FM_PNG_WINDOW = 32768)
Description:
  inf_copy() checks only `dist <= 0 || (size_t)dist > z->produced`. The window
  is a 32 KB ring (z->window[z->produced & 32767]). For dist > 32768, the byte
  at `from & 32767` has already been overwritten by newer output, so the
  decoder emits stale bytes instead of rejecting the stream. RFC 1951 limits
  distance to 32768.
Cause:
  Missing upper bound tied to FM_PNG_WINDOW.
Measured evidence (verbatim inf_put/inf_copy, ASAN+UBSAN harness):
  produced = 40000, older history = 0xAA, most recent 32768 bytes = 0xBB.
  inf_copy(dist = 32769, len = 1) returns 0 and emits 0xBB. The correct source
  byte (position 7231) is 0xAA and is no longer representable in the window.
  Expected behaviour: reject with FM_ERR_CORRUPTED.
Pseudo-fix:
    if (dist <= 0 || dist > (int)FM_PNG_WINDOW ||
        (size_t)dist > z->produced) return -1;
    /* FM_PNG_WINDOW is 32768; keep an assert that it stays 32768 because
       Deflate's distance limit is fixed by the format. */

D-03  PNG stored-block negative shift (UBSAN) and uint32 chunk-skip wrap
================================================================================
Class      : Undefined behavior (UBSAN) + integer wrap / parser desync
Location   : src/fm_png.c:456-479  (inf_stored)
             src/fm_png.c:711-723  (png_skip)
             src/fm_png.c:725-809  (png_need, line 779: png_skip(len + 4u))
             src/fm_png.c:998-1035 (png_decode pre-IDAT loop, line 1030)
             src/fm_png.c:669-709  (png_read, mem_pos + n)
             src/fm_png.c:1134-1165(png_out_bytes, mem_len + n)
Description:
  (a) `len |= inf_get(z) << 8;` and `nlen |= inf_get(z) << 8;` shift a negative
      int when the stored-block header is truncated at EOF. inf_get() returns
      -1. UBSAN reports "left shift of negative value -1". The `< 0` check at
      line 466 happens too late.
  (b) `png_skip(in, len + 4u)` is called with a raw uint32 chunk length. For
      len = 0xFFFFFFFF the addition wraps to 3, so the parser skips 3 bytes and
      then interprets payload as the next chunk header. On 32-bit targets,
      `r->mem_pos + n > r->mem_len` and `o->mem_len + n > o->mem_cap` can also
      wrap, permitting out-of-bounds reads/writes.
Measured evidence:
  Verbatim inf_stored with a 1-byte stream under UBSAN produced TWO runtime
  errors: "left shift of negative value -1" at the len and nlen compositions.
  `printf("inf_stored rc=%d")` then returned -1, i.e. the UB already happened.
  Arithmetic: (uint32_t)0xFFFFFFFF + 4u == 3u.
Pseudo-fix:
    static int inf_stored(Inf *z)
    {
        int b0, b1, b2, b3;
        uint32_t len, nlen;
        inf_align(z);
        b0 = inf_get(z); b1 = inf_get(z);
        b2 = inf_get(z); b3 = inf_get(z);
        if (b0 < 0 || b1 < 0 || b2 < 0 || b3 < 0) return -1;
        len  = (uint32_t)b0 | ((uint32_t)b1 << 8);
        nlen = (uint32_t)b2 | ((uint32_t)b3 << 8);
        if ((len ^ 0xFFFFu) != nlen) return -1;
        while (len-- > 0) { int b = inf_get(z);
            if (b < 0 || inf_put(z, (uint8_t)b) < 0) return -1; }
        return 0;
    }
    /* replace every png_skip(in, len + 4u) with a checked helper */
    static FM_Result png_skip_chunk(PngRead *r, uint32_t payload_len)
    {
        uint64_t skip = (uint64_t)payload_len + 4u;   /* + CRC */
        if (skip > UINT32_MAX) return FM_ERR_CORRUPTED;
        return png_skip(r, (uint32_t)skip);
    }
    /* and everywhere a size_t cursor is advanced: */
    if ((uint64_t)r->mem_pos + n > r->mem_len) return FM_ERR_EOF;
    if ((uint64_t)o->mem_len + n > o->mem_cap) return FM_ERR_TOO_LARGE;

4. LOWER-CONFIDENCE OBSERVATIONS (not counted as primary defects)
--------------------------------------------------------------------------------
O-01  Image_StreamDecode (src/fm_image.c:905-971) uses stack
      `internal[FM_INTERNAL_BUFFER_SIZE]` (512 by default, overridden to 4096
      by the host Makefile line ~105) and correctly rejects row_bytes > buffer.

7. ASAN / UBSAN-SAFE RATIONALE FOR THE PROPOSED FIXES
--------------------------------------------------------------------------------
  * Every width*height*bpp multiply is done in uint64_t and compared to
    SIZE_MAX and to the real capacity BEFORE the size_t cast (D-08, D-09).
    Image_BufferSize() (fm_image.c:99-121) is the existing model.
  * Canonical Huffman codes are validated with the `left` Kraft computation;
    huff_decode() additionally checks `off >= 0`, `off < count` and
    `index+off < nsym` before touching symbol[] (D-01).
  * Deflate distance is clamped to FM_PNG_WINDOW (32768) AND to z->produced,
    so window[from & 32767] can only address bytes that are still valid (D-02).
  * No `int` is shifted before its sign is known: inf_get() results are read
    into four ints, checked `< 0`, then composed into uint32_t (D-03). This
    removes the two measured UBSAN reports.
  * `len + 4u` and every `cursor + n` are computed in uint64_t; UINT32_MAX /
    mem_len / mem_cap checks happen before the cast or seek (D-03).
  * Validate BOTH data_capacity and nonzero data_size before any pixel loop,
    memcpy or memmove (D-07). Never memcpy from a pointer whose valid length
    has not been established.
  * Keep all static scratch inside the existing guards: fm_image.c under
    `#if FM_USE_IMAGE` (line 16 / 1907), fm_jpeg.c under
    `#if FM_USE_IMAGE && FM_USE_JPEG` (21), fm_png.c under
    `#if FM_USE_IMAGE && FM_USE_PNG` (21), fm_mjpeg.c under
    `#if FM_USE_MJPEG` (14). Add NO new globals (D-04, D-10, S1).
  * Use FM_Lock()/FM_Unlock() for g_icodec, g_png_* and g_image_work*, or move
    the state into caller-owned contexts (D-04, D-06, S7).
  * Decoder loops stay bounded by row_len / MCU counts / 32 KB window / 15-bit
    Huffman length. No unaligned casts, no signed overflow, no
    implementation-defined shifts. Disabled APIs keep returning
    FM_ERR_UNSUPPORTED via the existing stubs (S5).
  * No new heap slurp: fixes only add scalar checks and, optionally, a caller
    -provided scratch struct. The streaming IDAT / picojpeg / BMP row paths are
    untouched (S2). Add a probe byte cap for O-05 if adopted.
  * Measured sanitizer evidence supporting the above:
      - 200000 randomized invalid Huffman tables + huff_decode under
        ASAN+UBSAN: no crash (so D-01 is correctness, not OOB).
      - Verbatim inf_stored on a 1-byte stream: 2x UBSAN "left shift of
        negative value -1" (D-03), reproducible before the fix.
      - Verbatim inf_copy with dist=32769: returns 0 and emits stale 0xBB
        (D-02), reproducible before the fix.
      - `make asan` on the current tree: sanitizer linked (39 symbols), zero
        ASAN/UBSAN/LSan diagnostics; only the unrelated Audio test fails.

## V1 — `ebml_read`: بایتِ طول از حافظهٔ خوانده‌نشده (بحرانی)

**Describe.** برای هر عنصر EBML با ID یک‌بایتی (مثل `Timecode=0xE7`, `SimpleBlock=0xA3`, `PixelWidth=0xB0`, `TrackNumber=0xD7`) مقدار `Size` از یک بایتِ **content** خوانده می‌شود، نه از بایتِ خودِ Size؛ یا اگر `slen>1` باشد اصلاً بایت اول در دست نیست.

**Root cause.** در `fm_video.c:1796` فقط ۱ بایت خوانده می‌شود؛ در `1799` فقط وقتی `ilen > 1` باشد دوباره خوانده می‌شود. بعد `1802` بایتِ Size را از `hdr[ilen]` می‌گیرد که برای `ilen==1` هرگز پر نشده (و برای `ilen==2` هم بعد از `read(pos, len=3)` بایتِ سومِ Size در `hdr[2]` نیست و در `hdr[3..]` است). سپس `1804-1813` شرط `ilen+slen>8` است و فقط در آن حالت درست جابه‌جا می‌کند.

**اثبات عددی (کد دست‌نخورده + پرینت موقت).** یک MKV حداقلیِ معتبر ساختم؛ `PixelWidth/PixelHeight` درست خوانده شد (`320x240`) اما:
```
[inner] cpos=101 cend=175 rc=0 cid=E7 csz=2      ← Timecode (سایز ۲) → سایز 950 خوانده شد
[inner] cpos=105 cend=175 rc=0 cid=A3 csz=68     ← SimpleBlock
[blk]   tnum=1 hlen=4 csz=68
[mkv]   count=1 audio=0                          ← فقط ۱ فریم از ۴ فریم لِیس‌شده، audio=0
```
بازهٔ عنصر `Timecode` به‌جای ۲ بایت، ۹۵۰ بایت شد → `cpos` پرش کرد → بقیهٔ بلوک‌ها/ترک صوتی گم شدند. با یک `ebml_read` بازنویسی‌شده (فقط برای تست، در `/tmp`) همان فایل `count=1, audio=2, arate=44100` داد.

**Proposed fix (قطعه‌کد، apply نشده):**
```c
static FM_Result ebml_read(FM_Video *v, uint64_t pos, uint64_t file_end,
                           uint32_t *id, uint64_t *size, uint64_t *data_off)
{
    uint8_t all[16];
    uint32_t ilen, slen, i;
    uint64_t sz = 0;

    if (pos + 2u > file_end) return FM_ERR_CORRUPTED;
    if (video_read_at(&v->file, pos, all, 1) != FM_OK) return FM_ERR_CORRUPTED;
    ilen = ebml_id_len(all[0]);
    if (ilen == 0u || ilen > 4u) return FM_ERR_CORRUPTED;          /* ID ≤ 4 B */
    if (pos + ilen + 1u > file_end) return FM_ERR_CORRUPTED;
    /* ALWAYS re-read ID+first size byte, whatever ilen is */
    if (video_read_at(&v->file, pos, all, ilen + 1u) != FM_OK) return FM_ERR_CORRUPTED;

    *id = 0;
    for (i = 0; i < ilen; i++) *id = (*id << 8) | all[i];

    slen = ebml_size_len(all[ilen]);
    if (slen == 0u || slen > 8u) return FM_ERR_CORRUPTED;
    if (pos + ilen + slen > file_end) return FM_ERR_CORRUPTED;
    if (slen > 1u &&
        video_read_at(&v->file, pos + ilen, all + ilen, slen) != FM_OK)
        return FM_ERR_CORRUPTED;                                   /* V2 هم رفع */

    sz = (uint64_t)(all[ilen] & (uint8_t)(0xFFu >> slen));
    for (i = 1; i < slen; i++) sz = (sz << 8) | all[ilen + i];
    if (sz == ((slen == 8u) ? UINT64_MAX : ((1ULL << (7u * slen)) - 1ULL)))
        sz = file_end - (pos + ilen + slen);                        /* unknown */
    *size = sz;
    *data_off = pos + ilen + slen;
    return FM_OK;
}
```

## V2 — همان تابع: سرریز `uint8_t hdr[8]` (ASAN/UBSAN)

**Describe.** `slen` می‌تواند ۵..۸ باشد و `ilen` تا ۴ → `ilen+slen` تا ۱۲.

**Root cause.** `1791` بافر ۸ بایتی است؛ `1819` با `hdr[ilen+i]` تا ایندکس ۱۱ می‌رود (خواندن OOB). در شاخهٔ `1804` هم `slen` بایت در `hdr[0..slen)` نوشته می‌شود که اگر `slen==8` سقف است ولی ایندکس‌گذاری بعدی (`hdr[ilen]`) دیگر بی‌معنی می‌شود.

## V3 — MKV `SamplingFrequency` به‌صورت float64 خوانده می‌شود (بالا)

**Describe.** همهٔ فایل‌های MKV واقعی (mkvmerge/ffmpeg) `Audio\SamplingFrequency (0xB5)` را به‌صورت **IEEE float** (۸ بایت) می‌نویسند. کد فعلی آن را به‌صورت **unsigned int big-endian** تجزیه می‌کند و همان بیت‌ها را `double` تفسیر می‌کند.

**Root cause.** `fm_video.c:1906`: `uint64_t u` از بایت‌ها ساخته می‌شود، بعد `le` با معکوس‌کردن ترتیب بایت‌ها و `memcpy(&d,&le,8)` → عددی ~`6.9e-310` → `(uint32_t)arate == 0` → `44100` فالبک. یعنی **نرخ نمونهٔ واقعی گم می‌شود** و در MKV با ۴۸ کیلوهرتز، صدا ۸٪ کندتر/کوتاه‌تر پخش می‌شود (drift تجمعی).

**تأیید عددی:** با `SamplingFrequency` مطابق spec (float64 = 44100) → `arate=0.0`؛ با یک uint ساختگی هم ۰. یعنی هیچ‌کدام از دو حالت درست خوانده نمی‌شود.

**Proposed fix:**
```c
/* EBML float: 4 or 8 bytes, big-endian IEEE-754 */
static FM_Result ebml_read_float(const uint8_t *b, uint32_t n, double *out)
{
    if (n == 4u) { uint32_t u = video_be32(b); float f; memcpy(&f,&u,4); *out = (double)f; return FM_OK; }
    if (n == 8u) { uint64_t u = video_be64(b); double d; memcpy(&d,&u,8); *out = d; return FM_OK; }
    return FM_ERR_CORRUPTED;
}
...
else if (aid == 0xB5u) {                       /* SamplingFrequency */
    uint8_t b[8];
    uint32_t n = (asz > 8u) ? 8u : (uint32_t)asz;
    if (n >= 4u && video_read_at(&v->file, adata, b, n) == FM_OK) {
        double hz = 0;
        if (ebml_read_float(b, n, &hz) == FM_OK && hz >= 1000.0 && hz <= 768000.0)
            arate = (uint32_t)(hz + 0.5);
    }
}
```
و در `Audio\Channels (0x9F)` که ۱ بایت فرض شده، برای `asz>1` عدد را از چند بایت big-endian بسازید:
```c

    if (n >= 1u && video_read_at(&v->file, adata, b, n) == FM_OK) {
```

## V8 — فهرست فریم ثابت: کلیپ بلند در AVI/MP4 «کوتاه» می‌شود (متوسط)

## V9 — MP4 `avcC`: `lengthSizeMinusOne` نادیده گرفته می‌شود (بالا)

**Describe.** `mp4_parse_avcc` (`1026-1099`) صریحاً `hdr[4]` را دور می‌ریزد («assumed 4-byte lengths») و `video_read_annexb` (`2385-2417`) همیشه `video_be32` می‌خواند. NAL با طول ۱ یا ۲ بایت (که در avcC مجاز است) به‌صورت نویز تجزیه می‌شود.

**Root cause.** عدم ذخیرهٔ `lengthSizeMinusOne` (۲ بیت پایین `hdr[4]`) در `FM_VideoPriv` و استفادهٔ ثابت ۴ در تبدیل.

**Proposed fix:**
```c
/* FM_VideoPriv: uint8_t nal_len_size;  // 1..4 */
priv->nal_len_size = (uint8_t)((hdr[4] & 0x03u) + 1u);

static FM_Result video_read_annexb(FM_File *f, uint64_t offset, uint32_t size,
                                   uint32_t nal_len_size, uint8_t *out,
                                   size_t cap, size_t *out_len)
{
    uint8_t hdr[4];
    uint32_t pos = 0;
    if (size > cap) return FM_ERR_TOO_LARGE;
    if (nal_len_size < 1u || nal_len_size > 4u) return FM_ERR_CORRUPTED;
    while (pos + nal_len_size <= size)
    {
        uint32_t nlen = 0;
        if (video_read_at(f, offset + pos, hdr, nal_len_size) != FM_OK) return FM_ERR_CORRUPTED;
        for (uint32_t i = 0; i < nal_len_size; i++) nlen = (nlen << 8) | hdr[i];
        if (nlen == 0u || (uint64_t)pos + nal_len_size + nlen > size)
            return FM_ERR_CORRUPTED;              /* V9-b: NAL ناقص دیگر پذیرفته نشود */
        memcpy(out + pos, "\0\0\0\1", 4);         /* خروجی همیشه 4 بایتی می‌ماند */
        if (video_read_at(f, offset + pos + nal_len_size,
                          out + pos + 4, nlen) != FM_OK) return FM_ERR_CORRUPTED;
        pos += 4u + nlen;                          /* ← بافر باید nal_len_size+4 جا داشته باشد */
    }
    *out_len = pos;
    return FM_OK;
}
```
(توجه: با این تغییر، طبق کامنت موجود در `2381-2384`، اندازهٔ خروجی دیگر هم‌اندازهٔ ورودی نیست؛ `cap` در `Video_DecodeFrame` باید `sps_pps_len + fsize + 4 * (تعداد NAL)` باشد، یا از همان ابتدا NAL به NAL بنویسید و در جا تبدیل کنید.)
همچنین در `2410` حالت «پایان با کمتر از ۴ بایت باقی‌مانده» بی‌صدا و بدون خطا به `FM_OK` می‌رسد؛ آن را `FM_ERR_CORRUPTED` کنید.

## V10 — MP4 H.265: `hvcC` پارس نمی‌شود (بالا)

**Describe.** برای `hvc1/hev1/h265` فقط `width/height` خوانده می‌شود (`fm_video.c:1533-1546`). اما برخلاف H.264، هیچ دیکودر HEVC درخت نمی‌تواند بدون `VPS/SPS/PPS` کار کند و `avc1`/`sps_pps` تنها برای H.264 پر می‌شود. بنابراین حتی وقتی یک دیکودر HW/SW ثبت شود، **همیشه** شکست می‌خورد.

**Proposed fix:** معادل `mp4_parse_avcc` برای `hvcC`:
```c
/* hvcC: [22] bytes of config, then numOfArrays; each array:
 *   byte0 = (array_completeness<<7) | (NAL_unit_type & 0x3F)
 *   word  = numNalus, then repeated { word len, len bytes }          */
static FM_Result mp4_parse_hvcc(FM_Video *v, Mp4Box *hvcc, FM_VideoPriv *priv)
{
    uint8_t h[23];
    if (hvcc->size < 8u + 23u) return FM_ERR_CORRUPTED;
    if (video_read_at(&v->file, hvcc->data, h, 23) != FM_OK) return FM_ERR_CORRUPTED;
    priv->hvc_len_size = (uint8_t)((h[21] & 0x03u) + 1u);       /* lengthSizeMinusOne */
    uint32_t num_arrays = h[22];
    uint32_t off = 23, end = (uint32_t)(hvcc->size - 8u);
    priv->sps_pps_len = 0;                                       /* همان بافر Annex-B */
    for (uint32_t a = 0; a < num_arrays; a++)
    {
        uint8_t ah[3];
        if (off + 3u > end || video_read_at(&v->file, hvcc->data + off, ah, 3) != FM_OK)
            return FM_ERR_CORRUPTED;
        uint32_t nals = video_be16(ah + 1); off += 3u;
        for (uint32_t n = 0; n < nals; n++)
        {
            uint8_t lb[2];
            if (off + 2u > end || video_read_at(&v->file, hvcc->data + off, lb, 2) != FM_OK)
                return FM_ERR_CORRUPTED;
            uint32_t nlen = video_be16(lb); off += 2u;
            if (!nlen || off + nlen > end ||
                priv->sps_pps_len + 4u + nlen > sizeof(priv->sps_pps)) return FM_ERR_CORRUPTED;
            memcpy(priv->sps_pps + priv->sps_pps_len, "\0\0\0\1", 4);
            priv->sps_pps_len += 4u;
            if (video_read_at(&v->file, hvcc->data + off,
                              priv->sps_pps + priv->sps_pps_len, nlen) != FM_OK)
                return FM_ERR_CORRUPTED;
            priv->sps_pps_len += nlen; off += nlen;
        }
    }
    return FM_OK;
}
```
و در `Video_ReadFrame` برای `FM_VIDEO_CODEC_HEVC` همان مسیر `priv->avc1` (پیشوند SPS/PPS + تبدیل طول‌دار → Annex-B با `hvc_len_size`) اجرا شود. `SPSPPS_MAX` فعلی ۵۱۲ بایت است؛ برای HEVC باید بزرگ‌تر شود (VPS+SPS+PPS می‌تواند > ۵۱۲ باشد) — مثلاً ۱۰۲۴ و بررسی سرریز در بالا دیده شده است.

## V11 — HW decoder abstraction: فقط تا `MPEG4` (بالا)

**Describe.** قید کار «H264/H265 internal HW else SW» است. اما:

* `fm_hw.c:14-17`: `codec_valid()` فقط `RAW..MPEG4` را می‌پذیرد؛ `FM_VIDEO_CODEC_HEVC=6, VP8=7, VP9=8, AV1=9, THEORA=10` بیرون‌اند. آرایه `g_hw[FM_VIDEO_CODEC_MPEG4 + 1]` هم فقط ۵ خانه دارد.
* `Video_DecodeFrame` (`2591-2630`) پس از HW فقط برای `H264` و `MJPEG` فالبک SW دارد؛ برای بقیه `FM_ERR_UNSUPPORTED` برمی‌گرداند.

**تأیید عددی:**
```
register H264 (3) -> 0        (OK)
register HEVC (6) -> -1       (INVALID_ARGUMENT)
register VP9  (8) -> -1
register AV1  (9) -> -1
HWDecoder_Get(HEVC) = (nil)   ← حتی اگر ثبت هم شود، هرگز پیدا نمی‌شود
```
یعنی **HEVC هرگز HW نمی‌شود** و هیچ مسیر SW هم ندارد — دقیقاً نقض قید «H265 internal HW else SW».

**Proposed fix:**
```c
/* fm_hw.c */
static const FM_VideoCodecOps *g_hw[FM_VIDEO_CODEC_COUNT];   /* ← آرایه با اندازهٔ کامل */

static FM_Bool codec_valid(FM_VideoCodec codec)
{
    return (codec > FM_VIDEO_CODEC_UNKNOWN && codec < FM_VIDEO_CODEC_COUNT);
}

/* fm_video.c — انتخاب صریح: HW اول، بعد SW، و در نهایت خطای گویا */
static const FM_VideoCodecOps *video_pick_codec(FM_VideoCodec c)
{
    const FM_VideoCodecOps *hw = HWDecoder_Get(c);
    if (hw != NULL) return hw;                       /* H264/H265 HW */
#if FM_USE_H264
    if (c == FM_VIDEO_CODEC_H264) return H264_GetCodecOps();
#endif
#if FM_USE_MJPEG
    if (c == FM_VIDEO_CODEC_MJPEG) return MJPEG_GetCodecOps();
#endif
    return NULL;                                     /* HEVC/VPx/AV1 → HW لازم */
}
```
و در `Video_DecodeFrame` وقتی `video_pick_codec()` نال بود، به‌جای `FM_ERR_UNSUPPORTED` یک `FM_ERR_LOG` یک‌باره بزنید («HEVC needs HWDecoder_Register»). در `fm_video.h` هم `FM_VIDEO_CODEC_COUNT` به enum اضافه شود تا اندازهٔ آرایه همیشه هم‌گام بماند.

## V12 — YUV420→RGB888: crop (`left`/`top`) نادیده گرفته می‌شود (بالا)

**Describe.** `h264bsdCroppingParams` سه‌گانهٔ `left/top/width/height` می‌دهد. کد فعلی فقط `cw/ch` را می‌گیرد و `left`/`top` را دور می‌ریزد، بعد از `Y[0]` شروع می‌کند:

```c
/* fm_h264.c:441-450 */
if (!crop_flag) { cw = buf_w; ch = buf_h; }
...
yuv420_to_rgb888(pic, buf_w, buf_h, cw, ch, (uint8_t *)frame_out);  /* left/top گم */
```
برای هر streaم با `frame_cropping_flag==1` (تقریباً همهٔ ۱۹۲۰×۱۰۸۰ که بافر ۱۹۲۰×۱۰۸۸ است، و خیلی از ۴۸۰/۵۷۶) نتیجه: **۴ تا ۸ پیکسل جابه‌جایی + ۲ خط سبز/فتیله در پایین و راست**.

ضمناً `simple_video.h` در مسیر HW-JPEG یک `sw_convert(..., s.crop...)` دارد که از `FM_Image` می‌آید و *معنای متفاوتی* برای crop دارد؛ اگر همان مقدار به دیکودر H.264 هم داده شود، دو نوع crop قاطی می‌شوند.

**Proposed fix:**
```c
/* fm_h264.c */
static void yuv420_to_rgb888_crop(const uint8_t *yuv, uint32_t w, uint32_t h,
                                  uint32_t left, uint32_t top,
                                  uint32_t cw, uint32_t ch, uint8_t *rgb)
{
    const uint8_t *Y = yuv;
    const uint8_t *U = yuv + (size_t)w * h;
    const uint8_t *V = yuv + (size_t)w * h + ((size_t)w * h) / 4u;

    for (uint32_t y = 0; y < ch; y++)
    {
        const uint32_t sy = top + y;
        for (uint32_t x = 0; x < cw; x++)
        {
            const uint32_t sx = left + x;
            const int yy = Y[(size_t)sy * w + sx];
            const int uu = U[(size_t)(sy / 2u) * (w / 2u) + (sx / 2u)] - 128;
            const int vv = V[(size_t)(sy / 2u) * (w / 2u) + (sx / 2u)] - 128;
            /* ... همان ضرایب فعلی ... */
            uint8_t *p = rgb + ((size_t)y * cw + x) * 3u;
            p[0] = (uint8_t)clamp8(yy + ((359 * vv) >> 8));
            p[1] = (uint8_t)clamp8(yy - ((88 * uu + 183 * vv) >> 8));
            p[2] = (uint8_t)clamp8(yy + ((454 * uu) >> 8));
        }
    }
}
...
h264bsdCroppingParams(h->storage, &crop_flag, &left, &cw, &top, &ch);
if (!crop_flag) { left = top = 0u; cw = buf_w; ch = buf_h; }
if (left + cw > buf_w || top + ch > buf_h) { left = top = 0u; cw = buf_w; ch = buf_h; }
if ((uint64_t)cw * ch * 3u > frame_cap) return FM_ERR_TOO_LARGE;
yuv420_to_rgb888_crop(pic, buf_w, buf_h, left, top, cw, ch, (uint8_t *)frame_out);
```
**نکتهٔ مهم:** خروجی دیگر `info.width/height` (از کانتینر) نیست، بلکه `cw/ch` است. باید `v->info.width = cw; v->info.height = ch;` پس از اولین دیکود به‌روز شود، وگرنه `Video_DecodeFrameAs/Scaled` با ابعاد کانتینر (مثلاً ۱۹۲۰×۱۰۸۰) روی بافر `cw×ch` کپی می‌کند. پیشنهاد: در `h264_decode` یک `out_w/out_h` در `H264Ctx` نگه دارید و از `Video_DecodeFrame` بعد از `decode_frame` بخوانید (نیاز به یک `get_frame_size` اختیاری در `FM_VideoCodecOps` — بک‌ورد-کامپتیبل با `NULL`).

**همچنین:** کل این تبدیل ~۳ میلی‌ثانیه در ۳۲۰×۲۴۰ و ~۵۰ میلی‌ثانیه در ۷۲۰×۴۸۰ روی H7 است (دو ضرب + clamp برای هر پیکسل). برای «HW path» پیشنهاد: اگر `HWDecoder_Register(H264/DMA2D-YCbCr)` موجود باشد، همان مسیر مستقیم YCbCr→RGB565 را استفاده کنید (`examples/dma2d_ycbcr.h`) تا کپی/تبدیل نرم‌افزاری حذف شود. ضمناً تبدیل فعلی **full-range BT.601** فرض می‌کند؛ برای ویدئوی `video_full_range_flag=0` (محدودهٔ ۱۶..۲۳۵) رنگ‌ها washed-out می‌شوند. `h264bsdVideoRange()` و `h264bsdMatrixCoefficients()` موجود است:
```c
const FM_Bool full = h264bsdVideoRange(h->storage) ? FM_TRUE : FM_FALSE;
/* limited range: Y' = (Y-16)*255/219 , C' = (C-128)*255/224 */
```

## V13 — `Video_ReadAudioFrame`: `init/close` و `FM_Alloc` برای هر پکت (بالا)

**Describe.** در `fm_video.c:3157-3178` برای *هر* پکت صوتی، `ops->init(&ctx, &ai)` صدا زده می‌شود و در پایان هر مسیر `ops->close(ctx)`. برای FLAC/Vorbis/Opus این یعنی بازسازی کامل وضعیت دیکودر.

**اثر:** در ۴۳ فریم/ثانیه (۲۲ کیلوهرتز) → ۴۳ `init/close` و ۴۳ جفت `FM_Alloc/FM_Free` در ثانیه روی heap آدرس‌پذیر SDRAM؛ روی مسیر I2S با بودجهٔ ۱۸۶ میلی‌ثانیه، هر بار تکه‌تکه‌شدن heap و (در بدترین حالت) `NO_MEMORY` زودگذر.

**نکتهٔ مثبت (هشدار):** برای **Opus** نگه‌داشتن context بین پکت‌ها *الزامی* است (حالت داخلی + FEC/PLC) — نسخهٔ فعلی عملاً Opus را هم بی‌صدا می‌کند.

**Proposed fix (reuse decoder ctx/ops):**
```c
typedef struct {
    const FM_AudioDecoderOps *ops;   /* مالک: جدول رجیستری (نپاکید) */
    void   *ctx;
} FM_VideoAudioDec;

/* در FM_VideoPriv */
FM_VideoAudioDec adec;

/* در open/close ویدیو */
static void video_audio_dec_close(FM_VideoPriv *p)
{
    if (p->adec.ctx && p->adec.ops && p->adec.ops->close)
        p->adec.ops->close(p->adec.ctx);
    p->adec.ctx = NULL; p->adec.ops = NULL;
}

static FM_Result video_audio_dec_get(FM_Video *v, const char *tag)
{
    FM_VideoPriv *p = (FM_VideoPriv *)v->priv;
    if (p->adec.ops && strcmp(p->adec.ops->name, tag) == 0) return FM_OK;  /* reuse */
    video_audio_dec_close(p);
    const FM_AudioDecoderOps *ops = Audio_GetDecoder(tag);
    if (!ops || !ops->decode) return FM_ERR_UNSUPPORTED;
    FM_AudioInfo ai = {0};
    ai.sample_rate = p->audio_rate ? p->audio_rate : 44100u;
    ai.channels    = p->audio_channels ? p->audio_channels : 2u;
    ai.bits_per_sample = 16u;
    (void)strncpy(ai.codec, tag, sizeof(ai.codec) - 1u);
    if (ops->init && ops->init(&p->adec.ctx, &ai) != FM_OK) return FM_ERR_NO_MEMORY;
    p->adec.ops = ops;
    return FM_OK;
}
```
سپس در `Video_ReadAudioFrame` به‌جای `ops->init`/`ops->close` از `p->adec.ctx` استفاده کنید و آن را فقط در `Video_Close` و `Video_SeekAudio` (برای پرشِ ناپیوسته) ببندید. `audio_part_off/left` هم همان‌طور می‌ماند.

## V18 — `h264_decode_attempt`: هر خطای ترمیم‌نشده = «فریم خراب» (متوسط)

**Describe.** هنگام `H264BSD_ERROR`، بایت‌ها تا start-code بعدی رد می‌شوند؛ اگر `k + 2 >= len` شد، **بدون هیچ فریم تولیدشده** `FM_ERR_INVALID_FORMAT` برمی‌گردد (`fm_h264.c:500-533`). این حالت برای «NAL دنباله (AUD/SEI) در انتهای فریم» یا «پکت بریده‌شده در EOF» طبیعی است.

**اثر مخرب:** `h264_decode()` این خطا را «زنجیرهٔ مرجع شکسته» تفسیر می‌کند → `bad_run++` → **ریست دیکودر + پخش مجدد keyframe** (`h264_reset_decoder` + `FM_Alloc` مجدد DPB). یعنی در یک کلیپ سالم می‌توانید هر چند فریم یک بار، دیکودر را کامل خراب/بازسازی کنید؛ روی H7 این ~۱۰۰ میلی‌ثانیه است و دقیقاً همان «stutter دوره‌ای» است که در `docs/REGRESSION_AUDIO_STUTTER.md` به گردن SD/SPI انداخته شده بود.

**Proposed fix:** تفکیک «خطای سوختگی» از «بدون تصویر»:
```c
enum { H264_OUT_PIC = 0, H264_OUT_NO_PIC, H264_OUT_ERROR };
static int h264_decode_attempt(..., uint32_t *out_status);
...
    if (k + 2 >= len)
    {
        /* NAL ناقص/دنبالهٔ پایان فریم: اگر تا اینجا تصویری تولید شده،
         * این خطا را نادیده بگیر؛ وگرنه NO_PIC (نه ERROR). */
        *out_status = any_pic ? H264_OUT_NO_PIC : H264_OUT_ERROR;
        return (*out_status == H264_OUT_NO_PIC) ? FM_OK : FM_ERR_INVALID_FORMAT;
    }
```
و در `h264_decode` فقط `H264_OUT_ERROR` باعث `bad_run++/reset` شود؛ `NO_PIC` فقط `FM_ERR_EOF`-مانند گزارش شود.

## V19 — MKV audio: index/streaming ناسازگار و CodecPrivate ۵۱۲ بایتی (متوسط)

**Describe.**
1. `FM_VIDEO_MAX_FRAMES` هم برای **فریم ویدئو** و هم برای **پکت صوتی** استفاده می‌شود (`priv->frames[]` و `priv->audio_frames[]`). در MKV، پکت‌های صوتی چند برابر ویدئو هستند، پس برای یک کلیپ ۲ دقیقه‌ای، ایندکس صدا در ~۲۵ ثانیه پر می‌شود. مسیر «streaming continuation» فقط برای AVI نوشته شده (`avi_audio`, `audio_scan_pos`)، پس MKV/MP4 بعد از پر شدن ایندکس **بی‌صدا** می‌شوند (`v->audio_frame_index >= priv->audio_count` → `FM_ERR_EOF`).
2. `priv->audio_private[512]` برای MKV CodecPrivate. `A_VORBIS` در MKV سه هدر Xiph است و setup header می‌تواند > ۵۱۲ باشد → `mkv_priv_sz <= sizeof(...)` شرط است و در غیر این صورت **بی‌صدا** رد می‌شود؛ در MP4 امضای `dfLa` هم می‌تواند بزرگ باشد.
3. `mkv_read_string` (`1825-1830`) با `sz >= cap` صرفاً برش می‌زند؛ `"V_MPEGH/ISO/HEVC"` داخل ۶۴ بایت جا می‌شود ولی `A_MS/ACM` با پارامترهای طولانی نه.

**Proposed fix:**
* یک آرایهٔ index جدا برای صدا با سقف مستقل (`FM_VIDEO_MAX_AUDIO_FRAMES`) یا اسکن مبتنی بر «آفست پکت + طول» با `cluster_idx` و `block_idx` به‌جای جدول کامل (چون MKV/Cues آفست کلاستر می‌دهد).
* `audio_private` را بزرگ‌تر و قابل‌تنظیم کنید (`FM_VIDEO_AUDIO_PRIVATE_MAX`, پیش‌فرض ۴۰۹۶) و در صورت کمبود، CodecPrivate را با `FM_Alloc` نگه دارید.
* در `Video_GetAudioInfo`، `sample_count` را از `audio_total` (که در MKV هرگز پر نمی‌شود!) یا از `DefaultDuration` و تعداد پکت‌ها محاسبه کنید.

## V20 — `Video_DecodeFrame`: alloc در مسیر داغ + گارد نبودن `pixels_cap` (متوسط/پایین)

**Describe.**
1. `2660`: برای هر فریم `FM_Alloc(cap)` و `FM_Free` — در ۳۰ fps یعنی ۶۰ فراخوانی تخصیص‌دهنده در ثانیه روی SDRAM (درست همان‌جایی که `simple_video` دنبال بودجهٔ ۶۶ میلی‌ثانیه است). `Video_DecodeFrameScaled` هم `2844` یک `FM_Alloc(native)` برای هر فریم دارد.
2. `2660` `pixels_cap` را بررسی نمی‌کند؛ فقط پلاگین بررسی می‌کند (`fm_h264.c:446`). یک پلاگین HW سفارشی می‌تواند سرریز کند. برای مسیر `RAW` هم (`2681`) `Video_ReadFrame(..., pixels_cap, ...)` بررسی می‌کند، خوب است.

**Proposed fix:**
```c
/* بافر صحنه (scratch) به‌اندازهٔ بزرگ‌ترین فریم، یک‌بار در Open یا به‌صورت lazy */
if (priv->scratch == NULL || priv->scratch_cap < cap) { /* realloc با سقف */ }
/* و گارد صریح قبل از فراخوانی پلاگین */
if ((uint64_t)v->info.width * v->info.height * 3u > pixels_cap) return FM_ERR_TOO_LARGE;
```
(با توجه به V12 که `cw/ch` ممکن است کمتر از `info` باشند، این گارد باید بعد از به‌روزرسانی ابعاد اعمال شود.)

## 1. `File_Move` — NULL check + `VFS_Resolve` error propagation

### F-01 — NULL path arguments are dereferenced through the resolver
* **File:line:** `src/fm_file.c:1470`–`1483` (`File_Move`), reached from `FM_VFS_Resolve` (`src/fm_filesystem.c:612`)
* **Describe.** `File_Move()` has no `NULL` guard, unlike every other public entry point in the
  file (`File_Delete` `FM_CHECK_PTR` at `:994`, `File_Copy` at `:1411`, `File_Rename`: no guard but
  `FM_VFS_Resolve` returns `INVALID_ARGUMENT`). `FM_VFS_Resolve()` does return
  `FM_ERR_INVALID_ARGUMENT` for `NULL`, but `File_Move` throws that away and returns
  `FM_ERR_NOT_FOUND`.
* **Root cause.** The first resolve is written as a boolean test with a hard-coded error:

```c
if (FM_VFS_Resolve(src_path, &m1, r1, sizeof(r1)) != FM_OK) {
    return FM_ERR_NOT_FOUND;              /* every cause becomes NOT_FOUND */
}
```
* **Observed.**
  `File_Move(NULL, "/b")` → `-3 (not found)`; `File_Move("/nomount/x", …)` → `-3`;
  `File_Move("/"+200 chars, …)` → `-3` while `File_Open` on the same path says
  `-16 (too large for buffer)`; `File_Move("relative", …)` → `-3` (should be `INVALID_PATH`).
* **Proposed fix.** Guard both arguments, and propagate `r` from *both* resolves;
  only fall through to copy+delete when the destination really resolves.

```c
FM_Result r;
FM_Bool dst_existed = FM_FALSE;

if (src_path == NULL || dst_path == NULL) {
    FM_Core_SetLastError(FM_ERR_INVALID_ARGUMENT);
    return FM_ERR_INVALID_ARGUMENT;
}
r = FM_VFS_Resolve(src_path, &m1, r1, sizeof(r1));
if (r != FM_OK) { FM_Core_SetLastError(r); return r; }      /* was: return NOT_FOUND */
r = FM_VFS_Resolve(dst_path, &m2, r2, sizeof(r2));
if (r != FM_OK) { FM_Core_SetLastError(r); return r; }      /* was: ignored */
if (m1 == m2 && m1->fs->ops.rename != NULL) {
    r = m1->fs->ops.rename(m1->fs, r1, r2);
    FM_Core_SetLastError(r);
    return r;
}
```
* **Test/A (repro).**

```c
File_WriteText("/mv_a.txt", "0123456789");
expect(File_Move(NULL, "/mv_b.txt", NULL, NULL)              == FM_ERR_INVALID_ARGUMENT);
expect(File_Move("/mv_a.txt", NULL, NULL, NULL)              == FM_ERR_INVALID_ARGUMENT);
expect(File_Move("/nomount/x.txt", "/mv_c.txt", NULL, NULL)  == FM_ERR_NOT_MOUNTED);
expect(File_Move("/mv_a.txt", "/nomount/y.txt", NULL, NULL)  == FM_ERR_NOT_MOUNTED);
expect(File_Move(long_path_over_FM_PATH_MAX, "/mv_b.txt", NULL, NULL) == FM_ERR_TOO_LARGE);
expect(File_Move("relative.txt", "/mv_b.txt", NULL, NULL)    == FM_ERR_INVALID_PATH);
```
  Before: `-3, -1, -3, -3, -3, -3`. After: `-1, -1, -18, -18, -16, -2`.

### F-02 — cross-mount rollback deletes a pre-existing destination
* **File:line:** `src/fm_file.c:1495`–`1506`
* **Describe.** On the copy+delete path, if the source delete fails the destination copy is
  removed to "keep the move atomic". If the destination existed **before** the call (and was
  overwritten by `File_Copy`), the rollback destroys the caller's data and cannot be undone:
  the source is still present, the old destination is gone.
* **Root cause.** Rollback without a pre-condition, plus overwrite-by-default in `File_Copy`.

```c
r = File_Delete(src_path);
if (r != FM_OK) {
    (void)File_Delete(dst_path); /* rollback: undo the copy */
}
```
* **Observed.** Read-only source adapter (`delete_file` → `ACCESS`) + pre-existing
  `/dst.txt = "IMPORTANT-PRE-EXISTING-DESTINATION"`: `Move → -4 (access denied)`,
  `/dst.txt exists=0`, `/ro/src.txt still exists=1`.
* **Proposed fix.** Record pre-existence and only remove what this call created (or refuse to
  overwrite without an explicit flag — `FM_TransferOpts.no_overwrite` already exists at the
  transfer layer but is not reachable from `File_Move`).

```c
(void)File_Exists(dst_path, &dst_existed);
r = File_Copy(src_path, dst_path, progress, user_data);
if (r != FM_OK) return r;
r = File_Delete(src_path);
if (r != FM_OK && !dst_existed) {
    (void)File_Delete(dst_path);   /* only what we created */
}
```
* **Test/B (repro).** Mount a `FM_FS` whose `ops.delete_file` returns `FM_ERR_ACCESS` at
  `/ro`; `File_Move("/ro/src.txt", "/dst.txt")` where `/dst.txt` pre-exists.
  Assert: return `FM_ERR_ACCESS`, `/ro/src.txt` exists, **`/dst.txt` unchanged**.

## 2. `File_PoolDump` — internal / external must be printed separately

### F-03 — merged counter is printed as if it were the internal pool
* **File:line:** `src/fm_file.c:410`–`448` (`File_PoolUsed`, `File_PoolDump`)
* **Describe.** `File_PoolUsed()` returns `internal + external`, and `File_PoolDump()` prints
  that total against `FM_MAX_OPEN_FILES` with the word *internal*, while the pool array
  `g_pool[]` is exactly `FM_MAX_OPEN_FILES` entries. With 2 external (`File_OpenEx`) handles
  open the header claims `3/8 internal` although only **1** of the 8 slots is used. The
  external registry is also bounded by the same `FM_MAX_OPEN_FILES` (`:582`–`:598`) but shows
  up under the pool's index numbering (`[x%lu]`), so the two limits cannot be told apart.
* **Root cause.** One counter for two independent resources; the diagnostic exists precisely
  for the `FM_ERR_NO_MEMORY (-14)` "handle leak" case (`include/fm_file.h:52`–`57`), where the
  distinction is the evidence that identifies the leak.
* **Observed.** `FM_MAX_OPEN_FILES=8`, 1 pool handle + 2 external handles:
  `File_PoolUsed() = 3`, dump header `file pool: 3/8 internal`.
* **Proposed fix.**

```c
void File_PoolDump(void)
{
    uint32_t i, internal = 0u, external = 0u;

    for (i = 0; i < FM_MAX_OPEN_FILES; i++) {
        if (g_pool[i].used) internal++;
        if (g_external_files[i] != NULL && g_external_files[i]->used) external++;
    }
    FM_Log("file pool: %lu internal / %lu external (slots %u)",
           (unsigned long)internal, (unsigned long)external,
           (unsigned)FM_MAX_OPEN_FILES);
    for (i = 0; i < FM_MAX_OPEN_FILES; i++) {
        if (g_pool[i].used) FM_Log("  [i%lu] %s", (unsigned long)i, g_pool[i].path);
        if (g_external_files[i] != NULL && g_external_files[i]->used)
            FM_Log("  [x%lu] %s", (unsigned long)i, g_external_files[i]->path);
    }
}
```
  (Keep `File_PoolUsed()`'s total semantics for its documented use — "count only"; add
  `File_PoolUsedSplit(uint32_t *internal, uint32_t *external)` if the UI needs both.)
* **Test/C (repro).** Open 1 handle with `File_Open` and 2 with `File_OpenEx`; capture the
  `FM_Log` sink (`FM_Log_SetSink`), call `File_PoolDump`, assert the header contains
  `1 internal / 2 external` and that the `[i…]`/`[x…]` tags match the handle kinds.

## 3. `File_Copy` — partial destination must not survive a failure

### F-04 — truncated destination left behind (and an intact one destroyed)
* **File:line:** `src/fm_file.c:1441`–`1464`
* **Describe.** The destination is opened with `CREATE|TRUNCATE` before the first byte is read.
  If `FM_File_CopyStream()` or `File_Close(dst)` fails, the function returns the error but
  leaves whatever was written (0 … n bytes) at `dst_path`. `FM_Transfer_CopyEx()`
  (`src/fm_transfer.c:171`–`176`) does delete the incomplete copy — `File_Copy` does not, so
  the two copy APIs disagree, and `File_Move`'s cross-mount path inherits the hole.
  A pre-existing destination is truncated to 0 and silently replaced by a partial file.
* **Root cause.** No cleanup/rollback after the stream; the open order also means the old
  content is destroyed *before* it is known that the copy can succeed.
* **Observed.** 40 000-byte source, destination side returns `FM_ERR_NO_SPACE` after 5 000
  bytes: `File_Copy → -5 (no space left)`, `destination exists=1 size=5000`.
* **Proposed fix.** (a) cleanup on every failure path; (b) better: copy to `dst + ".fm_tmp"`
  (the same pattern `file_edit()` already uses at `:1536`) and `File_Rename` on success, so the
  destination is never observed half-written and a pre-existing destination survives a failure.

```c
r = FM_File_CopyStream(src, dst, progress, user_data);
if (r == FM_OK) { r = File_Close(dst); dst = NULL; }
if (r != FM_OK) {
    if (dst != NULL) (void)File_Close(dst);
    (void)File_Close(src);
    (void)File_Delete(dst_path);     /* no truncated destination */
    FM_Core_SetLastError(r);
    return r;
}
```
  Minimal version shown; the temp-file + rename version is preferable and matches `file_edit`.
* **Test/D (repro).** Mount a wrapper `FM_FS` over POSIX whose `file_write` returns
  `FM_ERR_NO_SPACE` after N bytes; `File_Copy` a file larger than N; assert
  `r == FM_ERR_NO_SPACE` **and** `File_Exists(dst) == FM_FALSE`; repeat with a pre-existing
  destination and assert its old content is unchanged (temp-file variant).

### F-05 — progress callback can report 100 % before the data is durable
* **File:line:** `src/fm_file.c:1394`–`1403` (`FM_File_CopyStream`)
* **Describe.** `progress(done, total, …)` is invoked as soon as the last chunk reaches
  `File_Write()`; no flush has happened yet. A power loss after the 100 % callback loses the
  tail of the file (nor flash / FATFS buffers). It is the classic "progress bar completes,
  file is short" symptom.
* **Root cause.** Reporting is tied to buffered writes, not to `File_Flush()`.
* **Proposed fix.** Flush before the final report:

```c
if (r == FM_OK) { r = File_Flush(dst); }
if (progress != NULL && r == FM_OK) { progress(done, total, user_data); }
```
* **Test/E.** Wrapper adapter that counts `file_flush` calls; assert one flush happens *before*
  the last progress callback and that `done == total` only after it.

## 4. `FM_Transfer_Raw` — range vs capacity validation, erase sizing

### F-06 — no range validation against `capacity` (writes past the device)
* **File:line:** `src/fm_transfer.c:345`–`361` (guards), `396`–`434` (loop)
* **Describe.** `FM_Transfer_Raw` checks `src->read`, `dst->write` and pointers — nothing else.
  `Storage_ReadBlocks`/`Storage_WriteBlocks`/`Storage_EraseBlocks` all enforce
  `offset > capacity || len > capacity - offset` (`src/fm_storage.c:503, 537, 570`), and the
  callback contract in `include/fm_storage.h:56`–`60` documents the drivers as thin wrappers.
  A driver that trusts the caller therefore gets `offset+len > capacity`; the transfer reports
  `FM_OK`. `Storage_ReadBlocks` is also the documented *public* way to reach a device, so the
  two entry points behave differently for the same illegal request.
* **Root cause.** Validation lives only in the convenience wrappers, not in the transfer.
* **Observed.** 1 024-byte destination, `FM_Transfer_Raw(src, 0, dst, 1008, 256, NULL)`
  → `FM_OK`, driver's last write ended at **1264** (240 bytes past the end).
* **Proposed fix.** Validate up front, in subtraction form (see F-08 — `offset+bytes`
  overflows `uint64_t`):

```c
if (bytes > 0u) {
    FM_CHECK(src_off <= src->capacity && bytes <= src->capacity - src_off,
             FM_ERR_INVALID_ARGUMENT, "source range past capacity");
    FM_CHECK(dst_off <= dst->capacity && bytes <= dst->capacity - dst_off,
             FM_ERR_INVALID_ARGUMENT, "destination range past capacity");
}
```
* **Test/F (repro).** Fake storage with `capacity = 1024` and an unchecked `write`;
  `FM_Transfer_Raw(s, 0, d, 1008, 256, NULL)` must return `FM_ERR_INVALID_ARGUMENT` and the
  driver must record **zero** writes. Same for `src_off = UINT64_MAX - 8` (no overflow wrap).

### F-07 — one unaligned, oversized erase request; `(uint32_t)` truncation
* **File:line:** `src/fm_transfer.c:352`–`361`
* **Describe.** The whole destination range is erased in a single call,
  `dst->erase(dst, dst_off, (uint32_t)bytes)`, with three consequences:

  1. **Unaligned start/length.** NOR adapters accept only whole erase units —
     `block_storage_erase` (`src/fm_device.c:191`) and `flash_storage_erase`
     (`src/fm_device.c:369`) return `FM_ERR_INVALID_ARGUMENT` unless
     `offset % erase_size == 0 && length % erase_size == 0`. Because the error is returned
     as-is, the whole transfer aborts. `FM_Qspi_Erase` happens to round internally
     (`src/fm_qspi.c:646`–`651`) — and then erases the sectors *before* `dst_off`, i.e. data
     outside the requested region — so the two adapters behave inconsistently for the same call.
  2. **32-bit truncation.** `bytes` is `uint64_t`; `(uint32_t)bytes` is `0` for any
     `bytes` that is a multiple of 4 GiB — the region is *not erased* and is then programmed
     onto dirty flash.
  3. **No progress / no cancel.** Hours of sector erase with no `progress` callback.

  The chunk loop below already knows the unit (`unit_mask`, `to_edge`); the erase does not.
* **Root cause.** The erase is modelled as one opaque call instead of per-unit work, and the
  width change 64 → 32 bits is unchecked.
* **Observed.**
  * 4 KiB erase unit, `FM_Transfer_Raw(src, 0, dst, 1024, 8192, NULL)`:
    `erase(off=1024, len=8192)` → driver rejects → `FM_ERR_INVALID_ARGUMENT`;
    zero erases, nothing copied.
  * `bytes = 0x1_0000_0000` → `erase(len=0)` → nothing erased.
* **Proposed fix.** Erase per destination unit, exactly aligned, with the 64-bit width kept:

```c
if (dst->erase != NULL && bytes > 0u) {
    uint64_t left = bytes;
    uint64_t at   = dst_off;
    uint32_t unit = dst->erase_size;
    if (unit == 0u) unit = dst->write_size;
    if (unit != 0u) {
        if ((dst_off % unit) != 0u) return FM_ERR_INVALID_ARGUMENT; /* keep contract explicit */
        at = dst_off - (dst_off % unit);
    }
    while (left > 0u) {
        uint32_t n = (left > (uint64_t)unit) ? unit : (uint32_t)left;
        r = dst->erase(dst, at, n);
        if (r != FM_OK && r != FM_ERR_UNSUPPORTED) return r;
        if (r == FM_ERR_UNSUPPORTED) break;
        at += n;
        left = (left > (uint64_t)n) ? (left - n) : 0u;
        if (!xfer_report(o, done_erased, bytes)) return FM_ERR_CANCELLED;
    }
}
```
  (Or route the erase through `Storage_EraseBlocks`' validation and let the driver round —
  but pick **one** policy; today QSPI rounds down to the sector and CAP-block adapters refuse.)
* **Test/G (repro).** Storage with `erase_size = 4096` that records `(off, len)` and rejects
  non-multiples: `FM_Transfer_Raw(..., dst_off = 1024, 8192, …)` must succeed and produce
  exactly `2` erase calls of `4096` at `0` and `4096`; `bytes = 1ull << 32` must produce
  `1048576` calls (or be rejected by F-06's capacity check long before that).

### F-08 — `FM_Transfer_RawVerify` dereferences unvalidated callbacks
* **File:line:** `src/fm_transfer.c:446`–`482`
* **Describe.** Only `a`/`b` are null-checked; `a->read`/`b->read` are called directly.
  The public prototype (`include/fm_transfer.h:139`–`141`) promises the same inputs as
  `FM_Transfer_Raw`, so a storage without `read` crashes instead of returning an error.
* **Root cause.** The verify helper bypasses the guard block that `FM_Transfer_Raw` has.
* **Observed.** `FM_Transfer_RawVerify(&st, 0, &st2, 0, 16)` with `read == NULL` →
  **SIGSEGV** (exit 139).
* **Proposed fix.**

```c
FM_CHECK(a->read != NULL, FM_ERR_UNSUPPORTED, "source has no read function");
FM_CHECK(b->read != NULL, FM_ERR_UNSUPPORTED, "target has no read function");
if (bytes > 0u) {
    FM_CHECK(a_off <= a->capacity && bytes <= a->capacity - a_off,
             FM_ERR_INVALID_ARGUMENT, "verify range past source capacity");
    FM_CHECK(b_off <= b->capacity && bytes <= b->capacity - b_off,
             FM_ERR_INVALID_ARGUMENT, "verify range past target capacity");
}
```
* **Test/H (repro).** `FM_Transfer_RawVerify(&a, 0, &b, 0, 16)` with both `read == NULL`
  must return `FM_ERR_UNSUPPORTED` and must not crash.

### F-09 — `FM_Transfer_CopyEx(src == dst)` truncates the source
* **File:line:** `src/fm_transfer.c:97`–`112`
* **Describe.** `File_Copy` rejects a self-copy (`src/fm_file.c:1415`–`1432`, including the
  "same mount, same relative path" case), `FM_Transfer_CopyEx` does not: it opens the source
  for read, then opens the same path with `CREATE|TRUNCATE`, and copies zero bytes over it.
  The file is destroyed and `FM_OK` is returned.
* **Root cause.** The guard exists in one of two parallel implementations.
* **Observed.** `/same.txt` = 24 bytes → `FM_Transfer_Copy("/same.txt", "/same.txt", NULL)`
  → `FM_OK`, file is **0 bytes**. `FM_Transfer_Move` with equal paths would copy nothing and
  then delete the source, i.e. **data loss reported as success**.
* **Proposed fix.** Same resolve-and-compare block as `File_Copy` (or delegate:
  `FM_Transfer_Copy` → `File_Copy` when `verify`/`no_overwrite` are off, keeping one code
  path for copy semantics).
* **Test/I (repro).** `File_WriteText("/same.txt", "…")`; expect
  `FM_Transfer_Copy("/same.txt", "/same.txt", NULL) == FM_ERR_INVALID_ARGUMENT` and size
  unchanged; same for `FM_Transfer_Move`.

### F-10 — descriptor left open, and failed content left in place, on the verify path
* **File:line:** `src/fm_transfer.c:191`–`227`
* **Describe.** `chk` is registered in the external handle registry by `File_OpenEx` (`:586`)
  and is closed only on the normal path at `:213`. The early returns at `:194` (`open` failed —
  harmless, nothing registered) and `:216` (`r != FM_OK` after the read loop) leave `chk`
  dirty: `f->used == 1`, `g_external_files[i] == &chk` pointing at a **stack object**, while
  `:214`'s close is skipped. Additionally the CRC-mismatch return at `:223`–`:226` leaves the
  corrupt destination on disk even though `verify` was requested.
* **Root cause.** Two early returns interleaved with the close; `File_OpenEx`'s registry entry
  is invisible to the caller; no cleanup on `FM_ERR_CORRUPTED`.
* **Proposed fix.**

```c
r = File_OpenEx(&chk, dst_path, FM_OPEN_READ);
if (r != FM_OK) return r;
/* … read loop, leaving the outcome in r … */
{
    FM_Result rc = File_Close(&chk);        /* ALWAYS close what we opened */
    if (r == FM_OK) r = rc;
}
if (r != FM_OK) return r;
if (out_info != NULL) { out_info->crc_dest = crc_dst; out_info->verified = FM_TRUE; }
if (crc_dst != crc_src) {
    (void)File_Delete(dst_path);            /* a failed verify is a failed copy */
    return FM_ERR_CORRUPTED;
}
```
* **Test/J.** Wrapper adapter whose `file_read` fails (`FM_ERR_IO`) on the *second* open of the
  destination, with `opts.verify = 1`; assert `File_PoolUsed()` is back to its previous value
  after the call (no leaked external slot) and that a corrupt destination is deleted on
  `FM_ERR_CORRUPTED` (inject a byte between write and verify).

### F-11 — intermediate buffer is neither cache-maintained nor re-entrant
* **File:line:** `src/fm_transfer.c:18`–`25` (`g_xfer_buf`), `415`–`428`; `src/fm_file.c:1529`
* **Describe.** The header promises "buffer cache Clean/Invalidate around each chunk when the
  other side is DMA" (`include/fm_transfer.h:24`–`26`). The implementation contains **no**
  cache operation: `grep -c FM_Cache_ src/fm_transfer.c` → 0. `FM_File_CopyStream()` and
  `file_edit()` share the single thread-local-free `FM_InternalBuffer()` (`src/fm_core.c:349`),
  so a `File_Copy` progress callback that itself calls `File_Insert`/`File_Copy` overwrites the
  chunk being copied.
* **Root cause.** The documented invariant is not implemented; one scratch buffer serves
  nested calls (only `FM_USE_THREADS` makes it thread-local, not recursion-safe).
* **Proposed fix.** (a) call `FM_Cache_CleanForDma(buf, len)` before `dst->write` and
  `FM_Cache_InvalidateAfterDma(buf, len)` after `src->read` when `FM_USE_DMA`; (b) keep a
  small in-use flag next to the buffer and return `FM_ERR_BUSY` for nested users instead of
  silently corrupting the copy.
* **Test/K.** With `FM_USE_DMA=1` and a driver that asserts
  `FM_Cache_DmaAligned(buf, len)`, run `FM_Transfer_Copy` of a 3-chunk file and assert the
  clean/invalidate counters equal the chunk count. Separately: a progress callback that calls
  `File_Copy` recursively must return `FM_ERR_BUSY` (or copy correctly), not corrupt data.

### F-12 — `FM_USE_CRC=0` does not link
* **File:line:** `src/fm_transfer.c:14`, `146`–`149`, `211`; `include/fm_config.h:79`–`81`;
  `src/fm_crc.c:8`
* **Describe.** `fm_crc.c` compiles its whole body out under `#if FM_USE_CRC`, but
  `FM_Transfer_CopyEx` calls `CRC_Compute32()` unconditionally (also `src/fm_mediacache.c:57`).
  `make fm_test FM_USE_CRC=0` fails at link:
  `undefined reference to 'CRC_Compute32'` (`fm_transfer.c:148`, `:211`, `fm_mediacache.c:57`).
* **Root cause.** The `verify` option is not gated, although it is documented as an optional
  feature and the header for it is compiled out.
* **Proposed fix.**

```c
#if FM_USE_CRC
    if (o->verify) { … }                     /* both call sites + the final compare */
#else
    if (o->verify) return FM_ERR_UNSUPPORTED; /* verify needs FM_USE_CRC */
#endif
```
* **Test/L.** CI target that builds with `FM_USE_CRC=0` (and `FM_USE_CACHE=0`,
  `FM_USE_THREADS=1`, `FM_USE_INTERNAL_BUFFER=0`) and must link; plus a runtime test that
  `FM_Transfer_CopyEx(..., {.verify=1})` returns `FM_ERR_UNSUPPORTED` in that build.

## 5. Cross-cutting findings (VFS / cache / semantics)

### F-13 — read cache is keyed per handle, so another handle's write is invisible
* **File:line:** `src/fm_file.c:112`–`196` (`FM_CacheLine.file` key), `720`–`770` (`File_Read`),
  `803`–`811` (write invalidation), `1333`–`1403` (`FM_File_CopyStream`)
* **Describe.** Cache lines are matched by `(f, offset)` where `f` is the `FM_File*`. `File_Write`
  invalidates only the writing handle's lines (`cache_invalidate_file(f)`). Any second handle on
  the same file — or the *same* path re-opened between two reads (`File_ReadAll` twice in a row,
  `FM_File_CopyStream`, `File_Insert`) — keeps serving pre-write bytes.
* **Root cause.** Invalidation by handle identity instead of by file identity (path/mount).
* **Observed.** Reader handle primed (`"AAAAAAAA"`), writer handle overwrites with
  `"BBBBBBBB"`, reader re-reads → `"AAAAAAAA"` while the backend holds `"BBBBBBBB"`.
* **Proposed fix.** Key cache lines by `(mount, resolved path)` instead of `FM_File*`, or flush
  **all** lines for a path on every write/rename/delete/truncate (cheap: `FM_CACHE_LINES=16`).
* **Test/M (repro).** Two handles on one path (`FM_OPEN_READ` / `FM_OPEN_WRITE`), overwrite
  through the writer, re-read through the reader; assert the new bytes. Also: read the whole
  file twice with `File_ReadAll` around an out-of-band write and assert the second read differs.

### F-14 — a hard I/O error is reported as `FM_OK` by the cached read path
* **File:line:** `src/fm_file.c:766`–`770`
* **Describe.** `return (total > 0) ? FM_OK : r;` discards any backend error once at least one
  byte was served, so `FM_ERR_IO`, `FM_ERR_TIMEOUT` and `FM_ERR_CORRUPTED` all look like a clean
  short read. Only `FM_ERR_EOF` should be masked. The non-cached path (`:776`–`790`) and the
  large-read fast path (`:687`) already behave correctly, so the bug appears only for
  `1 < len < 2 * FM_CACHE_LINE_SIZE` **and** `FM_USE_CACHE=1` — the configuration used by the
  host Makefile and by `FM_BUFFERS=LARGE` board builds.
* **Root cause.** A blanket "got some bytes" success rule instead of an EOF-specific one.
* **Observed.** 900-byte read, backend returns `FM_ERR_IO` on the second 512-byte block:
  `File_Read → 0 (OK), *read=512` — a truncated file reported as success.
* **Proposed fix.**

```c
if (r == FM_ERR_EOF) return FM_OK;          /* short read at EOF is fine */
return (total > 0 && r == FM_OK) ? FM_OK : r;
```
* **Test/N (repro).** Adapter that fails the second `file_read` with `FM_ERR_IO`; a 900-byte
  `File_Read` must return `FM_ERR_IO` (and `*read` may still be 512).

### F-15 — `file_edit()` temp name can overflow `FM_PATH_MAX`
* **File:line:** `src/fm_file.c:1536`–`1538`
* **Describe.** `strncat(tmp, ".fm_tmp", sizeof(tmp) - strlen(tmp) - 1)` silently truncates when
  the path is near `FM_PATH_MAX` (the `strncpy` above already consumed the space), so the temp
  file name collides with the original path or with another file's temp. `File_Insert`,
  `File_DeleteRange` and `File_ReplaceRange` then "replace" the wrong entry.
* **Root cause.** Unchecked concatenation onto a bounded buffer that is already full.
* **Proposed fix.** Refuse the edit when `strlen(path) + sizeof(".fm_tmp") > sizeof(tmp)`
  (`FM_ERR_INVALID_PATH`), or build the temp name from the directory + a short fixed suffix.
* **Test/O.** `File_Insert` on a path of length `FM_PATH_MAX - 3` must return
  `FM_ERR_INVALID_PATH` and leave every file untouched.

### F-16 — `File_Delete` / `File_Rename` are not path-normalization consistent
* **File:line:** `src/fm_file.c:988`–`1012`, `1024`–`1053`
* **Describe.** `File_Copy` normalizes and compares *resolved relative* paths before copying
  (`:1420`–`1432`), while `File_Move` compares raw strings (`:1417` in `File_Copy` only) and
  `File_Delete`/`File_Rename` do no self-comparison at all: `File_Delete("/a/./b")` and
  `File_Delete("/a/b")` reach the backend as different strings, and `File_Rename(p, p)` relies
  on the adapter (FMFS treats it as a no-op, POSIX `rename(2)` succeeds, but a FATFS adapter
  that maps it to "delete then create" would lose the file). Normalization must be one policy.
* **Root cause.** Path canonicalization is applied at the resolver, but several call sites
  still compare pre-normalized strings.
* **Proposed fix.** Use `FM_VFS_Resolve()` + `strcmp(rel)` (as `File_Copy` already does) for
  every self-comparison, and document `Rename(p, p)` as a no-op.
* **Test/P.** `File_Rename("/a/b", "/a/./b")` → `FM_OK`, file intact; `File_Delete("/a/./b")`
  removes the same entry as `File_Delete("/a/b")`.

۴.۲. تست تاییدیه WAV IMA-ADPCM (Audio #2 & #3)

    اشباع pred در int32_t و کلمپ علامت‌دار idx: ساخت یک بلاک ۸ بایتی IMA-ADPCM در حافظه/فایل شامل:
        بلاک الف: pred = 32700, idx = 88 (step = 32767) و نیبل 0x07 (افزایش شدید مثبت) ← نمونهٔ خروجی باید دقیقاً 32767 اشباع شود (نه منفی بر اثر سرریز int16_t).
        بلاک ب: pred = 0, idx = 0 (step = 7) و دو نیبل پیاپی 0x00 (index_delta = -1) و سپس نیبل 0x04 ← چون idx پس از گام اول باید روی 0 بماند (نه wrap به 255 -> 88)، نمونهٔ بعدی نباید جهش دامنه‌ای بیش از چند واحد داشته باشد (abs(sample) < 32).
    block_align فرد و فایل بریده‌شده در EOF (زیر UBSan/ASan):
        ساخت فایل WAV با format = 0x11 و block_align = 13 (فرد) و خواندن با Audio_Read تحت make asan (-fsanitize=address,undefined) ← عدم بروز خطای misaligned address روی int16_t*.
        نوشتن data_size = 64 در هدر WAV ولی بریدن فایل واقعی روی ۱۰ بایت از بخش data (معادل ۱ هدر ۴ بایتی + ۶ بایت نیبل = ۱۳ نمونه) ← Audio_Read باید دقیقاً ۱۳ نمونه برگرداند و بایت‌های مقداردهی‌نشدهٔ ۵۴ بایت انتهایی بافر را دیکد نکند.
