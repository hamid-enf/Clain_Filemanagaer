# بررسی ReportV51 — فایل و ذخیره‌سازی

**وضعیت این سند مربوط به دور قبل است.** برای تغییرات و موارد باز جدید، [ادامهٔ اصلاحات](FILE_V51_REMEDIATION.md) را ببینید.

## دامنه و روش

`ReportV51.txt` سه گزارش A، B و C را کنار هم دارد. هر سه ممیزی، commit `78662328e727910eda54cac0b584c32710f24976` را هدف گرفته‌اند؛ مبنای کار حاضر `efd0347` است (از نظر کدِ مرتبط، بعد از `7866232` تغییر عملکردی گزارش‌شده‌ای اضافه نشده است). تاریخ 2026-11-14 در خود گزارش ذکر شده و در این محیط تأیید مستقلی برای تاریخ اجرا نداریم. فایل‌های evidence و harnessهای حسابرسان که به مسیرهای داخلی ماشین ایشان اشاره می‌کنند در مخزن همراه گزارش نیستند؛ اعداد و خروجی‌های آن‌ها در این سند «گزارش‌شده» هستند، نه بازاجرای مستقل ما.

ارزیابی زیر به معنی پایان ممیزی یا بی‌خطایی بخش فایل نیست. برای حفظ تمرکز و جلوگیری از راه‌حل ظاهری برای ownership و concurrency، فقط اصلاحات مشخص‌شده در جدول انجام شده‌اند. سایر موارد باز هستند. هیچ تست عملی برد انجام نشد.

## یافته‌های ممیز A

| شناسه | بررسی و وضعیت در این patch |
|---|---|
| A-01 | **باز، ریسک مهم از دست رفتن داده**. مسیرهای `File_Copy`, `File_SafeReplace`, editorهای متن، `File_Recover` و `Logger_Recover` روی نام مشتق‌شده فرض مالکیت می‌کنند؛ توصیف گزارش با کد سازگار است. یک `exists` قبل از open کافی نیست: race و crash/recovery و تعامل با actor خارجی نیاز به طراحی claim اتمیک و سیاست بازیابی دارند. |
| A-02 | **باز، ریسک مهم**. `FM_Transfer_CopyEx` مقصد را مستقیم باز می‌کند و در خطا حذف می‌کند. صرفاً حذف‌نکردن، محتوای قدیمی truncateشده را برنمی‌گرداند؛ نیاز به staging/verify/publish و قرارداد callback دارد. |
| A-03 | **باز**. تفاوت موقعیت بعد از truncate و مستند فعلی نیاز به تصمیم سازگاری بین backendها و تست هر backend دارد؛ FatFS ممکن است در seek فراتر از EOF رفتار خاص داشته باشد. تغییر مستند بدون حل اختلاف رفتاری کافی نیست. |
| A-04 | **اصلاح و بازتولید مستقل**. `File_Open` و `File_OpenEx` حالا `TRUNCATE` بدون `WRITE` را با `FM_ERR_ACCESS` قبل از open و ثبت handle رد می‌کنند؛ داده باقی می‌ماند. آزمون قبل از اصلاح شکست و پس از آن پاس شد. |
| A-05 | **باز**. شکست `Directory_Rewind` اسلات را آزاد می‌کند؛ مدیریت lifetime و بستن backend بدون دوباره‌بستن handle شکست‌خورده نیاز به بررسی دارد. |
| A-06 | **باز**. پردازش escapeهای JSON و تفاوت عمق writer/parser مستلزم decoder UTF-16 شامل surrogate، رد ورودی نامعتبر و بررسی سازگاری است؛ تغییری داده نشده. |
| A-07 | **اصلاح برای `Text_WriteLine`**. نوشتن کوتاه موفق تکرار می‌شود، پیشرفت صفر `FM_ERR_IO` است؛ تست متن کامل و پیشرفت صفر قبل از اصلاح شکست و پس از آن پاس شد. این به معنای ممیزی همه مصرف‌کنندگان `File_Write` نیست. |
| A-08 | **باز / قرارداد طول عمر**. pointer pool بعد از close معتبر نیست؛ جلوگیری واقعی از alias پس از reuse با pointer صرف قابل تضمین نیست و نیازمند تغییر طراحی API/handle است، نه فقط افزودن generation داخل همان slot. |
| A-09 | **باز، ریسک مهم**. `File_Copy` در برخی شرایط به direct-write fallback می‌رود؛ مستند header خود استثنا را ذکر کرده ولی این با عبارت all-or-nothing ناسازگار است. اصلاح نیازمند تعیین سیاست rename ناموجود، مسیر بلند و نام temp ناسازگار FatFS است. |
| A-10 | **باز**. ناهماهنگی کد خطا برای مسیر بلند، بدون تغییر. |
| A-11 | **باز**. `Directory_Rewind` last-error را تنظیم نمی‌کند. |
| A-12 | **باز / نیاز به تعیین قرارداد**. رفتار بعد از خطای listing و rewind بررسی هدفمند می‌خواهد؛ گزارش تغییر تکرارپذیر را اعلام کرده است. |
| A-13 | **مستند/باز**. پاک‌کردن مقصد پس از شکست verify در گزارش تأیید تجربی نشده؛ به redesign مورد A-02 وابسته است. |

## یافته‌های ممیز B

| شناسه | بررسی و وضعیت |
|---|---|
| B-01 و B-02 | **اصلاح و بازتولید مستقل پس از اصلاح**. پس از `FR_EXIST`، adapter نوع هر دو طرف را قبل از هر rename جانبی می‌خواند و جابه‌جایی بین file و directory را رد می‌کند. تست adapter با mock سه نسل و نیز FatFS واقعی ST روی RAM disk: هر دو طرف و داده حفظ شدند. سناریوی FatFS واقعی قبل از اصلاح در گزارش B بازتولید شده؛ در این دور baseline مستقل آن اجرا نشده است. همچنان rename-over در FatFS چندمرحله‌ای است، و crash-atomic یا rollback در هر خرابی تضمین نشده. |
| B-03 | **ادعای عمومی تأیید نشد**. adapter واقعاً شاخهٔ remove-then-rename برای `LFS_ERR_EXIST` داشت، اما در نسخهٔ vendored فعلی `lfs_rename_` خودش جایگزینی و type check را انجام می‌دهد و برای mismatch، `ISDIR/NOTDIR` برمی‌گرداند؛ متن گزارش مسیر error را با مسیر معمول اشتباه گرفته و برای قطع برق oracle ندارد. شاخهٔ حذف خطرناک به‌صورت دفاعی حذف شد. تست مستقل LittleFS روی RAM: mismatch حفظ می‌شود و rename-over فایل موفق است. این تست اثبات power-loss atomicity نیست. |
| B-04 | **محافظ برای read/write اضافه و تست میزبان شد**. شمارش صفر و ضربی که در `uint32_t` جا نشود رد می‌شوند؛ offset در حلقه bounce پیش از جمع widen می‌شود. تست fake storage با headers FatFS واقعی: درخواست عادی پاس و overflow بدون تماس با driver رد شد. ادعای وابستگی این سرریز به ظرفیت >2TiB لازم نیست؛ عامل مستقیم count و sector size است. مسیر `CTRL_TRIM` نیز محاسبه طول جداگانه دارد و در این patch بررسی/اصلاح نشده است. |

| شناسه | بررسی و وضعیت |

| C-06 | **باز**. finalize/recover logger مبتنی بر نام است؛ برخورد و مسابقه در publish/cleanup همچنان خطر دارند. |
| C-07 | **باز**. خطای حذف backup بعد از commit بلعیده می‌شود؛ سیاست وضعیت commit و cleanup لازم است. |
| C-08 | **باز / ابهام قرارداد**. خطای sync پس از انتشار می‌تواند به معنی تغییر namespace با دوام نامعلوم باشد. `FM_ERR_IO` فعلی فاز commit را منتقل نمی‌کند؛ نباید آن را الزاماً rollback تفسیر کرد. |
